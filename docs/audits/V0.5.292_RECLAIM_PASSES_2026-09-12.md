# Bounded physical reclaim passes

## Problem and scope

The offline reclaim CLI reopened the database and reconstructed its authenticated
reader for every small compaction pass. During the September12 US maintenance
window, one invocation took37.4seconds while native compaction reported8.9seconds.
Another took90.2seconds with32.7seconds of compaction. These are whole-invocation
measurements; they do not attribute every remaining second to database opening.
Repeated object decoding and setup can be avoided while keeping the same native
retirement operation and its durable journal.

## Change and boundaries

`retirement-reclaim` accepts `--max-passes-per-open` in1..16, default1, matching
the existing tombstone command's bound. It opens one database/reader and invokes
the unchanged native reclaim method for each selected pass. No consensus,
transaction, archive format, authorization format or journal format changes.

The CLI validates limits and checks filesystem reserves before database opening.
After opening and before every native invocation it measures actual hot/cold
free space again. It does not carry an earlier pass's estimated free space into
the next pass or treat reported SST shrinkage as new filesystem capacity. The
native method retains range selection, live-file estimates, flush/recheck,
compaction reserve checks and durable queue updates. The operator must still
fund the complete setup/native/recovery envelope and bound the whole process.

Completion and a pass without compaction or split progress return immediately.
A split-only pass may continue with a fresh bounded pass. A capacity probe,
reserve or native error propagates without retrying writes; the last committed
journal remains the authority for explicit resumption.

JSON work counters sum the passes performed in this invocation. Queue length
starts at the first pass and ends at the last. `passes_completed`,
`max_ranges_per_pass` and `max_estimated_input_bytes_per_pass` make the bounds
explicit. `total_reclaimed_physical_bytes` is the final cumulative journal value,
not a sum of cumulative values. Existing single-pass work fields retain their
meaning. Neither report proves that filesystem free space increased by exactly
the reported family shrinkage.

## Validation and deployment

Seven CLI regressions cover changed hot/cold capacity, one-byte reserve loss,
strict count/input limits, split-only progress, completion, zero-progress pause,
non-retried capacity/native errors and aggregate accounting. A real database
fixture creates and retires an archive segment, completes native compaction,
reads its archived block/transaction and verifies that an already-completed
journal is unchanged by a later invocation.

Run the CLI tests and the unchanged native retirement failure-boundary suite,
workspace Clippy/tests, dependency/security checks, standalone contracts/genesis,
frontend/SDK/deployment QA and four-validator release matrix. CI and tag-workflow
artifacts must pass before any production use. Only signed tag artifacts may be
installed; existing v0.5.291 maintenance scripts remain bound to their original
binary hashes and cannot use this candidate without new exact-plan qualification.

After signed qualification, measure complete invocation time, each native work
counter, actual filesystem capacity, original journal continuity and own-state
restart/fleet acceptance. This candidate is not evidence that fleet reclamation,
permanent archives or R2 exit have completed.
