# Canonical transaction metrics correction

Status: candidate, September 7. Signed v0.5.283 remains installed on four
validators. No historical counter correction or v0.5.284 deployment is claimed.

The explorer returned total5,923,873 and daily0 while new successful native
OracleAttestation transactions appeared. EU localhost sampling confirmed unchanged
total/daily counters as slots advanced12,494,650 to12,494,709. Refreshing the page
cannot repair a persisted server counter.

`commit_batch_with_block` stores execution and the canonical block anchor together.
It previously discarded the anchor's new-slot result. Later `put_block_atomic`
found an existing slot and skipped its metric update. The canonical execution
path introduced in v0.5.224 therefore bypassed counting. This behavior is not an
Archive V2 requirement. The same total appears in preserved July deployment
evidence; do not attribute its introduction to the recent Archive V2 activation.

The candidate stages total transactions, total blocks and UTC daily counters in
the block's durable RocksDB batch. In-memory publication follows write success;
reads and saves serialize across that publication. Both storage orders count
exactly once. Native oracle and EVM transactions count, consensus metadata does
not. A committed transaction remains counted regardless of its execution result.
Canonical read errors propagate before new-slot classification. Daily counts
use the block's UTC date so historical replay does not inflate today.

Regression coverage includes execution-first and anchor-first storage, repeated
secondary index completion, duplicate replay after reopening, empty and
consensus-only blocks, an actual read-only RocksDB write failure, restart after
durable write before memory publication, concurrent saves, midnight rollover,
corrupt canonical slot input and unchanged state-root calculation. The initial
canonical test failed0 versus expected1 on the signed283 source. The corrected
workspace passed3,231 tests in47 suites (three ignored doc examples), including
the source scanner and repair command. Workspace clippy, standalone contracts,
genesis WASM builds and frontend/deployment static checks passed. The complete
four-validator matrix and exact-tag signed release gates remain required.

`tests/live-transaction-metrics.py` measures each RPC's observed slot range and
compares total/daily/block deltas with every canonical block and parent hash in
that range. An idle window cannot pass transaction acceptance. The local harness
submits three funded local transfers after initial sampling, avoiding dependence
on external oracle feeds. Its failure
fixtures cover frozen/doubled counts, stale daily values and incomplete or
conflicting history. The four-validator matrix invokes it before and after
Archive V2 role admission and fresh rejoin; CI checks its failure behavior.

Backfill is a separate source-backed operation. Retain the prior durable counters,
bind an immutable canonical frontier, verify complete transaction source coverage
and independently compare reconstructed totals before applying any correction.
Apply with an idempotent record and abort on source, frontier or prior-counter
drift. The existing Testnet waiver covers unavailable signed bodies
2,872,006..4,298,999; an incomplete scan cannot silently turn these into zero
transactions. A verified historical prefix counter may be usable only with an
exact source/slot provenance proof. Mainnet and fresh networks have no waiver.
No repair amount or complete historical total has yet been established.

The offline `metrics-reconcile` command requires a regular checksum-bound plan,
the matching source manifest, an existing database and explicit stopped-validator
acknowledgment. The writable database lock excludes another database writer.
Operator preflight must separately prove the actual service stopped and validate
the source evidence; a checksum alone does not prove the manifest's claims.
The plan binds the current canonical tip/hash, prior durable/RAM counters and
current UTC date. It refuses decreasing totals or inconsistent block/day counts.
One synchronous batch writes the counters and preserves the plan plus previous
daily values. Repeating that exact evidence/plan is a no-op, even after subsequent
chain progress; changed plans or prior values fail closed. This command has no
RPC surface and starts no validator. Core tests cover failed read-only writes,
invalid/drifted plans, conflict refusal, durable restart and replay after progress.
No production repair plan has yet been authorized by source qualification or applied.

The native `profile-source` audit now reports `user_transaction_count`, counts by
UTC epoch day, predecessor hash and last-block hash. It verifies complete
transaction Merkle roots and canonical continuity. Its optional `--archive-root`
requires exact `--catalog-root`, `--network-id` and `--genesis-hash`; catalog-owned
blocks use authenticated read-only codec reads, with hot/cold fallback only
outside catalog coverage. A corrupt archive object cannot fall back to a hot
copy or be quarantined/moved by this audit. The one-million-slot bound remains.
Use a preserved immutable checkpoint and source objects, split a longer audit
into linked ranges, and compare independent source reports. This is a count
audit; it does not change live metrics or authorize a repair by itself.
