## Root cause

The `v0.5.278` repair tests covered exact state projection, atomic state write,
tip-anchor replacement, marker recovery, and idempotence. They did not seed a
production-shaped pending next-height consensus WAL before the out-of-band
state transition. A tip anchor is read by normal block construction, but WAL
recovery deliberately restores previously signed locks and proposal values for
slashing safety. Once an explicitly confirmed administrative transition changes
the parent root, those pending values cannot remain valid.

This is not an Archive V2 migration, compaction, object, or catalog failure. It
is a lifecycle defect in the Testnet-only stopped-state repair introduced in
`v0.5.278`.

## Correction

Discarding the pending WAL would let a validator sign a second value at a
height where a pre-repair commit may already exist. `v0.5.279` therefore keeps
the WAL byte-for-byte and moves the correction into the canonical block
lifecycle.

The recovery has two exact phases:

1. A stopped-state rollback accepts only the existing repair marker at the
   unchanged tip. It subtracts the 276-spore remainder from the marker-bound
   recipient, restores the exact source-proven stale position, proves that a
   forward projection reproduces the repaired pool byte-for-byte, reconstructs
   the recorded old pool hash and state root, removes the marker in the same
   atomic batch, and restores the old tip anchor. It never opens or writes
   `consensus.wal`.
2. At canonical post-block slot `12,333,500`, all validators deterministically
   run the existing exact projection after the block is stored and before the
   next height begins. The repaired pool and activation marker commit in one
   RocksDB batch; startup repairs the non-consensus sidecar anchor if a crash
   occurs immediately afterward. The next child certificate then carries that
   repaired root through consensus.

New out-of-band repair writes are refused by the `v0.5.279` administrative
command. It can only verify a repair already recorded by `v0.5.278` or by the
deterministic activation. The rollback is impossible after any post-repair
block commits, and both directions retain the exact chain ID, stale-row,
pending-exit, value, pool-hash, state-root, tip, block-hash, and confirmation
guards.

## Applicability

Fresh testnets and mainnet are unaffected. They do not contain this historical
MossStake row and the repair refuses every chain ID except
`lichen-testnet-1`. The scheduled repair is a consensus-critical state
transition for the preserved Testnet only. It does not change the BFT
algorithm, block format, wire format, checkpoint format, Archive V2 format, or
normal WAL recovery rule.
