# v0.5.275 Production-Readiness Addendum

Date: 2026-09-03

Status: narrow production-scale checkpoint-I/O successor to signed
`v0.5.274`. This is not deployment approval until protected CI, the immutable
tag workflow, provenance, checksums, detached ML-DSA signature, coordinated
fleet installation, and live checkpoint acceptance all pass.

## Live failure boundary

Signed `v0.5.274` was installed from release workflow `33723898975` on all
four Testnet validators without a reset or state copy. US, Singapore, and India
continued finality while EU remained fail-closed on its own preserved state.
At slot `12,298,000`, all three active validators captured the exact raw
hot-repair checkpoint and completed the bounded block and transaction
categories. Each then spent more than ten minutes in `account_txs` category 7
while remaining healthy and advancing the chain.

The live databases explain the scale discontinuity. Each source has roughly
1.47 million hot and 5.2 million cold account-history rows. That column family
is ordered by account before slot. The checkpoint exporter therefore traversed
the entire historical index and performed canonical block validation before it
discarded rows outside the 50,000-slot window. Many immutable legacy block SSTs
currently reside on the authenticated read-only emergency R2/FUSE bridge, so
those unnecessary old-block lookups became high-latency remote reads. This is
not an Archive V2 object-format or consensus failure, but it is unbounded
pre-activation checkpoint I/O and is not accepted for production.

The in-progress `v0.5.274` staging checkpoints remain unpublished. Validator
state, WAL, identities, keys, cold history, R2 objects, and the signed rollback
release remain intact. No incomplete checkpoint is advertised to EU.

## Narrow correction

- Reuse the existing Archive V2 segment-export algorithm that derives
  `account_txs` keys from canonical blocks in an exact slot range.
- Read only the checkpoint's advertised recent-history blocks, in 1,000-slot
  chunks, and derive the canonical account-history keys from their signed
  transactions.
- Point-check every derived key against hot and legacy-cold source indexes.
  Accept byte-identical duplicates; fail closed on a conflict or missing key.
- Apply the existing per-page materialization budget before each write and keep
  atomic staging/publication unchanged.
- Do not change consensus, wire format, checkpoint schema, Archive V2 format,
  catalog format, role policy, retention, or the historical-loss waiver.

The preserved-state four-validator gate exposed three independent maintenance
and test-orchestration boundaries after that original correction:

- A successful legacy reclaim pass returned before Archive V2 migration and
  could repeatedly win the next maintenance turn. The scheduler now records a
  one-pass handoff: reclaim may run once, the next eligible pass must run
  migration, and only then can reclaim become eligible again. This changes
  scheduling fairness only; it does not change migrated bytes, cursors,
  consensus, or either archive format.
- A legacy reclaim range derived from RocksDB live files could exceed the
  256 MiB compaction budget and permanently block every range behind it. Such a
  range is now split persistently at a real live-file key boundary, with a
  bounded number of splits per pass. Non-reducing or otherwise unsafe splits
  fail closed. Existing queue entries and receipts remain replay-safe.
- Four co-located validators captured raw checkpoints while holding their
  node-local archive-maintenance locks, then queued on one shared-disk
  materialization lock. The raw capture remains inside the archive boundary,
  but that node-local lock is now released before waiting on the shared-disk
  lock and reacquired after it is obtained. The materializer therefore sees a
  coherent durable hot/cold source without forming a maintenance-lock convoy.
  Separate production VPSs do not share this local filesystem lock, but the
  corrected ordering is valid for both layouts.

The exact gate also gained fail-closed resume boundaries for already-owned
validator state, idempotent reuse of a fully verified common catalog after a
capacity interruption, and checkpoint target selection that follows the real
1,000-slot pre-activation and 10,000-slot catalog-bound cadences. Resume checks
prove each node's RocksDB, key, identity, stake/epoch membership, genesis,
minimum slot, head spread, and chain liveness before continuing. They never
copy validator state and never convert an incomplete run into a passing one.

The same release also aligns the explicitly controlled LICN/USD reference at
`$0.15`. The value is the default for validator attestations, future testnet
and mainnet genesis, stale/offline display fallbacks, DEX liquidity tooling,
and the informational reward projection. It does not rewrite existing genesis;
the preserved testnet changes through signed validator quorum attestations
after coordinated deployment. External wrapped-asset prices remain sourced
from their configured market-data feeds.

This changes work from a full-history scan plus one old-block lookup per row to
bounded block traversal plus one source-index check per canonical row in the
checkpoint window. Memory is bounded by the 1,000-slot block chunk and the
derived rows for that chunk.

## Focused verification

The new regression creates valid slots 0 through 2, deliberately corrupts the
out-of-window slot-0 block body, and publishes a hot-repair checkpoint whose
history begins at slot 2. Publication succeeds, excludes slots 0 and 1, and
contains every account-history key derived from the canonical slot-2 block.
The old full-index path fails this case by decoding the irrelevant corrupt
slot-0 body.

Focused `hot_repair_` tests pass 6/6, including materialization budgets,
atomic unpublished failure, bounded cold history, the new account-history
derivation regression, and the queued-materializer lock-ordering regression.
Existing Archive V2 segment account-history derivation
and missing-source tests pass 2/2. The maintenance regressions cover the exact
44-range reclaim-starvation sequence, safe oversized-range splitting and
non-reducing-split refusal, and a queued materializer proving that it does not
hold the archive-maintenance lock.

The preserved four-validator gate then passed on one continuous set of four
independently owned states without genesis regeneration or chain replay:

- bounded legacy migration completed while consensus remained live; the V1
  cursor reached `3723` with `2002` migrated rows and the V2 cursor reached
  `1891` with `5971` migrated rows;
- a 96-transaction loaded backlog, live validator outage/catch-up, own-state
  restart, coordinated all-validator restart, proposer/voter participation,
  canonical certificate parity, and Archive V2 role/corruption/source-outage
  matrix all passed;
- all four independently published the same common Archive V2 catalog through

  `55934ff52eda3a0f883183c4335be4460f249230bf4d21c7a7376a94aae21f59`;
- all four captured and materialized exact slot `70,000` hot-repair

  `4e1e687bc2289be80b58919be90c2c90167d87a4d414f8e84804a3a19b55e222`;
- clean full-archive, verified-cache, and consensus-role joins copied no

This evidence preserves prior green gates rather than regenerating them after

and immutable-tag gates remain mandatory before release.

## Production boundary

Do not install a local candidate binary. The live `v0.5.274` fleet remains the
signed baseline until an exact `v0.5.275` tag artifact passes every gate.
Deployment is coordinated stop/install/start, preserves every node's own state
and WAL, and must reproduce matching bounded checkpoints from at least two
independent validators before EU imports one. Archive V2 activation and legacy
retirement remain blocked until four-validator own-state convergence and
catalog parity are proven. R2 deletion remains unauthorized.
