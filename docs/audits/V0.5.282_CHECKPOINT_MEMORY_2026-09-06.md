# v0.5.282 checkpoint memory and verification lifetime

Status: candidate. Signed v0.5.281 remains installed on Testnet; Archive V2
activation and complete release acceptance remain pending. Production OOM
acceptance is not closed by these diagnostic results.

## Confirmed cache-budget inconsistency

The live validator uses an explicitly configured 1 GiB hot database cache.
Hot-repair checkpoint construction also explicitly uses 128 MiB, but later
`StateStore::open_checkpoint` calls passed no cache bound. The database factory
therefore selected a separate host-derived cache of up to 4 GiB for background
checkpoint verification and snapshot serving. The live command-line cache
setting did not reach those consumers.

A regression against the v0.5.281 source opens an actual checkpoint and queries
RocksDB's cache-capacity property. It observes 4,294,967,296 bytes and fails the
134,217,728-byte bound. The correction passes with four simultaneous readers,
preserves the live database's independently configured cache, reads the same
checkpoint tip, and leaves checkpoint files unchanged. All 23 focused core
checkpoint tests pass, including hot/cold preservation, bounded history,
read-only roots, atomic publication and pruning.
All 67 focused validator checkpoint tests also pass, covering verification,
authenticity, export pins, disk-pressure reclamation, cache refresh, snapshots,
WAL preservation and recovery boundaries.

The production-shaped diagnostic uses the signed v0.5.281 validator's
read-only manifest command against an independently preserved EU checkpoint at
slot 12,407,000. Both runs use the same checkpoint files and a dedicated 2 GiB
memory cgroup, no swap, one CPU of quota, read-only filesystem protection,
network isolation and a 900-second deadline. A separate host-memory guard can
stop only the diagnostic job. No validator configuration, state or WAL is changed.

## Verification source lifetime

SEA's v0.5.281 journal also records checkpoint-manifest verification losing an
SST because normal checkpoint pruning removed its source while the scan was
still active. Snapshot transfer sessions already hold reference-counted export
pins; background and anchored verification did not. Both verification paths now
acquire the same pin before opening the checkpoint and release it after the
read-only store and verification work finish. Ordinary and disk-pressure pruning
already honor those pins. Missing/pruned sources still fail closed.

## Remaining acceptance

The change bounds checkpoint caches and protects verification sources. It does
not change consensus, state transitions, wire encoding, checkpoint contents,
Archive V2 formats or history policy. A cache limit is not a total process-memory
limit; live caches, memtables, allocator retention, RPC work and concurrent
maintenance must still fit the measured host budget.

Require protected CI, complete immutable release workflow, detached PQ checksum
signature, exact installed/running artifacts, the full four-validator matrix,
and sustained production memory under representative queries across published
checkpoints. Preserve OOM/restart history. Fresh networks and mainnet receive no
legacy-history waiver, and the current Testnet VPS storage is not approved for
indefinite archive growth or mainnet.
