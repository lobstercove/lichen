Lichen Architecture

A technical deep-dive into how Lichen is designed — from network gossip to state commitment. Lichen is an agent-first, high-performance Layer-1 blockchain with WASM smart contracts, on-chain reputation, and a Tendermint-style BFT consensus mechanism.

Overview

Lichen is structured as four distinct layers, each with a clear responsibility boundary. From bottom to top:

Network Layer (P2P)
Gossip protocol, peer discovery, block propagation, and RPC/WebSocket endpoints
Consensus Layer (Tendermint BFT)
Propose → Prevote → Precommit → Commit, 400ms target cadence, stake-weighted quorum
Execution Layer (WASM)
Wasmer runtime, contract execution, gas metering, host function interface
State Layer (RocksDB)
Account storage, contract data, block history, Merkle state roots

Each transaction flows downward through these layers: the Network layer receives it via RPC, Consensus orders it into a block, Execution runs the logic, and State persists the result. This separation allows each layer to be optimized independently.

Design Philosophy
Lichen is designed for agent-first applications. LichenID provides composable identity, names, vouching, skill attestations, bounded reputation, and recovery to contracts and clients. Base protocol mempool ordering and fees deliberately do not privilege reputation.

Tendermint BFT Consensus

Lichen uses Tendermint-style BFT, a leader-based consensus with deterministic finality: Propose → Prevote → Precommit → Commit.

Block Production

Block time targets a continuous 400ms slot cadence. Validators produce liveness blocks even when the mempool is empty, and transaction-bearing blocks use the same slot target.

Leader Selection

Leaders are selected deterministically with stake-weighted proposer priority. Reputation is not part of consensus voting power or proposer selection:

Formula 
voting_power = bonded_stake
proposer_priority += voting_power
selected_proposer_priority -= total_voting_power

Operational reputation and contribution telemetry can inform governance and monitoring, but cannot silently change the authenticated stake denominator used by consensus.

PBFT Finality

After a leader proposes a block, it enters the Tendermint-style voting round:

  1. Propose — The selected proposer broadcasts the candidate block.
  2. Prevote — Validators validate the proposal and sign a prevote.
  3. Precommit — A two-thirds prevote quorum permits a signed precommit.
  4. Commit — A two-thirds precommit quorum finalizes the block.

A block is considered finalized once 2/3+ of validators (by stake weight) submit commit votes. Under normal network conditions, Lichen targets finality on the 400ms slot cadence.

Canonical Finality Proofs

Every block after height 1 commits its parent's finality proof in an internal versioned consensus transaction. The proof contains a sorted quorum certificate and the complete sorted voting powers for the parent height. The parent header authenticates that denominator through validators_hash, so a validator-set change in the child cannot reinterpret the parent's two-thirds threshold. The certificate also commits the parent's complete post-effects state root. Proposal validation, peer sync, checkpoint verification, archive startup, and getBlockCommit verify the same parent-scoped proof.

Fast Finality
Unlike probabilistic finality chains (Bitcoin, Ethereum PoW), Lichen blocks are deterministically final once committed. There are no reorgs after finalization.

Transaction Lifecycle

Every transaction follows a defined path from submission to state commitment:

1
Submit
Client sends a signed transaction to any RPC node via sendTransaction. The node validates the signature, checks the nonce, and verifies the sender has sufficient balance for fees.
2
Mempool
Valid transactions enter the mempool ordered by effective compute-unit price, then total fee, then FIFO for ties. Sender reputation is accepted only for API compatibility and is ignored for ordering.
3
Block Assembly
The current slot leader collects transactions in the deterministic fee-priority order up to the block limits, computes a state-root preview, and constructs the block header.
4
Sign & Broadcast
The leader signs the block with their validator key and broadcasts it to all peers via gossip.
5
PBFT Vote
Validators independently execute all transactions in the block, verify the state root matches, and participate in the 3-phase PBFT voting round.
6
Finalize
Once 2/3+ commit votes are received, the block is marked as finalized. The finalized block header is gossiped to all nodes.
7
State Commit
Each node writes the finalized state changes to RocksDB, updates account balances, contract storage, and validator records. The Merkle state root is sealed into the block.

State Model

Lichen uses an account-based state model (not UTXO). All state is stored in RocksDB, organized into column families for efficient access patterns.

Column Families

Column Family Key Value Description
accounts Address (32 bytes) Account struct All user and program accounts
blocks Slot number (u64) Block struct Block headers and transaction lists
transactions Tx hash (32 bytes) Transaction + Receipt Full transaction data with execution results
contract_storage Program ID + key Arbitrary bytes Per-contract key-value storage
validators Validator pubkey ValidatorInfo struct Stake, score, vote history
metadata String key Varies Chain config, genesis hash, epoch info
account_snapshots Address (32) + Slot (8, BE) Account struct Historical account snapshots. Non-development testnet and mainnet validators enable archive mode automatically and use the archive-<network> sibling of their state directory for bounded retention. Query via getAccountAtSlot RPC.

Account Structure

Every account on Lichen has the following fields:

Rust 
pub struct Account {
    /// Native LICN balance in spores (1 LICN = 1e9 spores)
    pub balance: u64,

    /// Transaction sequence number (prevents replay attacks)
    pub nonce: u64,

    /// LichenID reputation score (0.0 – 100.0, stored as u32 * 100)
    pub reputation: u32,

    /// Amount of LICN staked in validator or delegation
    pub staked: u64,

    /// LichenID trust tier (0 = unverified, 1–6 = tier levels)
    pub trust_tier: u8,

    /// If this is a program account, the WASM bytecode hash
    pub program_hash: Option<[u8; 32]>,

    /// Arbitrary account data (up to 10 MB for program accounts)
    pub data: Vec<u8>,

    /// Account owner (system program or deploying program)
    pub owner: Pubkey,
}
Rent Exemption
Accounts must maintain a minimum balance proportional to their data size to remain rent-exempt. The formula is: min_balance = data_size × 6960 + 890880 spores. Accounts that fall below this threshold are garbage-collected after 2 epochs.

Archive V2 Public History

Archive V2 separates mutable consensus state from immutable public history. Validators retain a bounded recent-history window with current state and serve older canonical history from deterministic, checksummed segments admitted by a signed catalog.

LayerContentsInvariant
Hot state Current consensus state plus the configured recent public-history window Crash-recoverable RocksDB/WAL state; checkpointed coherently with archive inputs
Archive V2 segments Canonical blocks, transactions, indexes, events, trades, and account snapshots by bounded slot range Certificate-normalized deterministic bytes, content hashes, range roots, and explicit previous/following boundaries
Signed catalog Ordered segment identities and the admitted genesis-to-watermark range Activation fails closed on gaps, conflicts, signer mismatch, replica disagreement, or insufficient headroom
Replica domains Independent object-storage copies of the same catalog and segment objects Recovery copies; they do not replace local serving or authorize deletion by themselves

Legacy hot/cold history is a migration source, not a permanent second archive. It is removed only after four-way V2 manifest parity through a signed exact-range retirement followed by RocksDB compaction. Fresh networks start on this model and receive no historical-loss waiver.

WASM Execution

Lichen executes smart contracts using the Wasmer WebAssembly runtime with ahead-of-time (AOT) compilation for near-native performance. Contracts are compiled from Rust to wasm32-unknown-unknown and deployed as program accounts.

Host Functions

Contracts interact with the chain through a set of host functions injected into the WASM environment at runtime:

Gas Metering

Every WASM instruction consumes gas. The runtime injects metering checkpoints at basic block boundaries during AOT compilation. Base costs:

  • Arithmetic/logic ops: 1 gas per instruction
  • Memory load/store: 3 gas per instruction
  • storage_read: 200 gas + 1 gas per byte read
  • storage_write: 5,000 gas + 5 gas per byte written (new key) or 200 gas (update)
  • emit_event: 375 gas + 8 gas per byte of event data
  • cross_contract_call: 2,500 gas base + callee gas

The per-transaction gas limit is 200,000 by default. The per-block gas limit is 50,000,000.

Memory Model

Each contract execution gets an isolated linear memory space starting at 1 page (64 KB) and expandable to 256 pages (16 MB) via memory.grow. Memory is reset between calls — contracts cannot persist state in WASM memory across transactions. Use storage_get/storage_set for persistence.

Stack Depth Limit
WASM call stack depth is limited to 1024 frames to prevent stack overflow attacks. Cross-contract call depth is limited to 8 levels. Exceeding either limit aborts the transaction and consumes all gas.

LichenID Integration

LichenID is Lichen's on-chain identity and reputation contract. Contracts and clients can read its records and apply explicit application policies. It does not change base-protocol transaction ordering, fees, RPC rate limits, consensus voting power, or proposer selection.

Trust Tiers

Tier Name Score Range Protocol Priority Protocol Fee Discount Application Use
0 Newcomer 0 – 99 None None Explicit contract policy
1 Verified 100 – 499 None None Explicit contract policy
2 Trusted 500 – 999 None None Explicit contract policy
3 Established 1,000 – 4,999 None None Explicit contract policy
4 Elite 5,000 – 9,999 None None Explicit contract policy
5 Legendary 10,000+ None None Explicit contract policy

How Reputation Affects the Stack

  • Mempool: All transactions are ordered strictly by fee (highest first), then FIFO for equal fees. Reputation does not affect queue priority.
  • Fees: All accounts pay the same base-protocol rates; optional priority fees are explicit transaction fields.
  • Rate limiting: RPC rate limits are transport/operation controls, not LichenID privileges.
  • Consensus: Voting power and proposer selection are stake-weighted and independent of LichenID scores.
Building Reputation
Vouching, name registration, and skill changes apply contract-defined reputation effects. Typed or direct reputation updates require the LichenID admin. Decay is bounded and applied in 90-day periods; clients must not imply automatic credit for every transaction or governance action.

Privacy & Security

Lichen retains historical Poseidon2 commitments, nullifiers, and Merkle state. Proof scheme 0x01 is disabled because its AIR did not constrain private witnesses, so the current release makes no active shielded-privacy or proof-soundness claim.

Implementation Status (Current)

Area Status Notes
Core ZK modules (core/src/zk/*) Disabled / compatibility only Historical Poseidon2 state and legacy scheme decoding remain; all proof acceptance fails closed
Shielded pool contract (contracts/shielded_pool) Fail-closed compatibility ABI Direct WASM custody and mutation calls return ERR_NATIVE_ONLY
Runtime/RPC wiring Read-only Historical queries report disabled status; proof helpers and submissions return unavailable
Deployment/boot scripts Withheld No activation is permitted until a sound versioned verifier and migration pass review

Reactivation Requirements

  • Proof scheme: A new explicit version; no automatic reuse of scheme 0x01
  • Domain binding: Proof type, chain ID, network/genesis, and verifier version
  • Field / hash layer: Goldilocks arithmetic plus Poseidon2 hashing
  • Constraints: Commitments, nullifiers, ownership, Merkle inclusion/anchor policy, recipient binding, 64-bit ranges, exact conservation, and duplicate handling
  • Operations: Deterministic proof/instruction limits and verifier resource bounds
  • Migration: Explicit compatibility policy for historical commitments and custody

Historical Transaction Flows (Currently Rejected)

  • Shield (transparent → shielded): Creates a new note commitment from public funds
  • Unshield (shielded → transparent): Spends a note and reveals only the necessary public outputs
  • Transfer (shielded → shielded): Consumes note inputs, emits new commitments, was intended to preserve value in-circuit

Current Security Properties

  • Fail-closed: Legacy proofs are rejected before custody state changes
  • Atomicity: Shielded custody effects require one rollback-capable state batch
  • Exact state: Checked counters and strict commitment replay reject malformed state
  • Privacy boundary: Validator RPC does not parse private shielded witnesses while the proof service is disabled

Explorer and Docs Separation

Explorer pages are being kept telemetry-first (stats, transactions, nullifier checks). Architecture education and implementation details live in the Website and Developer Portal so chain observability stays cleanly separated from protocol documentation.

Keypair Encryption at Rest

CLI-managed keypairs are encrypted with AES-256-GCM (authenticated encryption with 12-byte random nonce). Encrypted keypair JSON uses encryption_version = 2 for the canonical AES-GCM format.

Faucet CORS Policy

The testnet faucet enforces an explicit origin allowlist (approved development origins + production domains) with restricted HTTP methods (GET/POST/OPTIONS) — replacing the previous permissive policy.

Network Topology

Lichen's network layer handles peer discovery, data propagation, and client connections.

Gossip Protocol

Nodes communicate over native QUIC with role-based peer limits (20 by default for validators) and a Kademlia routing table. QUIC's anonymous TLS certificate is only a carrier: an application-layer ML-DSA-65 and ML-KEM-768 handshake authenticates the peer and derives the encrypted session before any P2P message is accepted.

  • Typed gossip: Blocks, transactions, votes, and peer records use bounded message formats and validation before admission.
  • Discovery: Configured seeds, durable peer records, peer exchange, and Kademlia routing provide restart and topology recovery.
  • Abuse resistance: Connection, subnet, ASN-bucket, frame, and expensive-request limits fail closed.

No 1,000-node propagation result is claimed without a reproducible distributed benchmark artifact. Operators measure current propagation and consensus cadence from fleet telemetry.

Peer Discovery

New nodes discover peers through three mechanisms:

  1. Bootstrap nodes: Hardcoded seed nodes for initial connection (configurable per network)
  2. Peer exchange (PEX): Connected nodes periodically share their known peer lists
  3. DHT: A Kademlia-based distributed hash table for decentralized peer lookup

Bootstrap Nodes

Config 
# Public testnet bootstrap nodes (QUIC/UDP)
bootstrap_peers = [
    "seed-01.lichen.network:7001",
    "seed-02.lichen.network:7001",
    "seed-03.lichen.network:7001",
]

# Mainnet has not launched. A signed launch handoff will publish its seed set.

Block Sync

When a node falls behind (e.g., after restart or joining late), it uses snapshot sync to catch up efficiently:

  1. Download the latest finalized state snapshot (compressed RocksDB checkpoint) from an authenticated peer
  2. Verify its post-state root against the child-committed certificate, transaction Merkle proof, signed child header, and historical child finality powers
  3. Apply any remaining blocks since the snapshot was created
  4. Switch to normal gossip-based block following

Legacy full-archive snapshots use the 1,000-slot cadence. Archive V2 bounded hot-repair snapshots are generated every 10,000 slots (~67 minutes at the production slot target) so their physical public-history compaction cannot become a continuous validator workload. Typical sync time for a new node is under 2 minutes for testnet.

RPC & WebSocket Endpoints

Every full node exposes two client-facing interfaces:

  • JSON-RPC (HTTP POST, default port 8899) — Request/response queries and transaction submission. See API Reference.
  • WebSocket (default port 8900) — Persistent subscriptions for real-time block, transaction, and log events. See WebSocket Reference.
Rate Limiting
Public RPC endpoints enforce rate limits of 100 requests/second per IP. For higher throughput, run your own node or use LichenID-authenticated endpoints which allow up to 1,000 req/s for Tier 4+ accounts.
