Contract Architecture

Lichen's genesis catalog currently deploys 32 contracts across DeFi, DEX, NFTs, Identity, Infrastructure, Governance, Prediction, and Wrapped Assets. LICN is the native coin and is documented here as a native asset, not a deployed WASM contract. The catalog describes fresh-genesis intent, not proof that an existing network has completed every later accounting migration or service activation.

Evidence boundary: the cards below are selected source overviews, not live-service attestations or exhaustive ABIs. The machine-checked Source Export Matrix is authoritative for the current source tree. Release-WASM hashes, deployed code hashes, migrations, configuration, custody, reserves, provider capacity, liquidity, and network health are separate gates.

Integration tiers: when a contract has a first-class SDK helper, prefer that surface over generic ABI packing. Today the JS, Python, and Rust SDKs ship LichenIdClient for identity registration, profile/name reads, skills, vouches, premium-name auction flows, metadata/delegate/recovery flows, and agent endpoint/rate/availability updates, SporePayClient for the common streaming-payment flows, LichenSwapClient for pool discovery, quotes, liquidity reads, stats, and the common swap/liquidity writes, and ThallLendClient for the stable lending flow: deposits, withdrawals, borrows, repayments, liquidations, account/protocol reads, interest-rate reads, and stats, plus SporeVaultClient for vault/user/strategy reads, aggregate stats, and the common deposit/withdraw/harvest flow. BountyBoardClient covers exact bounty accounting, lifecycle, administration, and migration operations.

Everything else: most contracts in this catalog currently use the generic SDK contract-call surface plus contract-specific JSON-RPC reads. Use this reference page and the ABI docs below as the source of truth for those integrations.

WASM ABI Calling Convention

Lichen contracts compile to WASM and follow a unified ABI for argument passing. The runtime supports three modes — agents should use JSON mode for simplicity or Layout Descriptor mode for full control.

Argument Passing Modes
Mode Trigger Best For
JSON Auto-Encode Args start with [ (JSON array) CLI calls, agents — no manual encoding needed
Layout Descriptor Args contain a canonical 0xAB descriptor SDKs, binary callers — full stride control per param
Raw Pointer Layout Neither of above All-pointer functions (pubkeys only, no integers)
JSON Auto-Encode Mode

When argument bytes start with [, the runtime parses them as a JSON array and converts each element to binary with a 0xAB layout descriptor:

JSON Type WASM Param Encoding Stride
String (valid base58) I32 32-byte public key 32
String (non-base58) I32 UTF-8 bytes, zero-padded to next 32-byte boundary (max 224B) padded length
Number ≤ 255 I32 1 byte 1
Number 256–65535 I32 2 bytes LE 2
Number > 65535 I32 4 bytes LE 4
Boolean I32 1 byte (0 or 1) 1
Number / any I64 8 bytes LE 8

Example — lichen call <addr> register_identity '["8nRM2Fk...", 1, "agent-demo", 10]'

The runtime detects the JSON array, encodes: 0xAB 20 01 20 01 + [32B pubkey][1B: 1][32B: "agent-demo\0…"][1B: 10]

Layout Descriptor Mode (0xAB)

Binary callers construct 0xAB + N stride bytes + data. Each stride byte controls how the runtime interprets the corresponding parameter:

Stride Meaning
32 (0x20) Pointer — 32 bytes at that offset, WASM receives memory address
4 (0x04) u32/i32 — 4 LE bytes, WASM receives raw I32 value
2 (0x02) u16/i16 — 2 LE bytes, WASM receives raw I32 value
1 (0x01) u8/bool — 1 byte, WASM receives raw I32 value
8 (0x08) I64 — 8 LE bytes, WASM receives raw I64 value

The descriptor must contain exactly one valid stride for every WASM parameter, and those strides must cover the remaining payload exactly. For I32 parameters the valid scalar strides are 1, 2, and 4; pointer strides are 32 or greater. I64 parameters require stride 8. A raw argument buffer whose first byte happens to be 0xAB, including a contract or account address, remains raw unless the complete descriptor is canonical. Binary clients should use the SDK encode_layout_args helper instead of constructing descriptors manually.

Raw Pointer Layout

Without JSON or 0xAB prefix: every I32 param advances 32 bytes (treated as a pointer). Every I64 param advances 8 bytes. This mode works for all-pointer functions (e.g., transfer(from, to, amount)) but silently breaks functions with mixed pointer/integer I32 params.

Which pattern should I use?

Named exports (recommended for new contracts): Each public function is a separate WASM export (#[no_mangle] pub extern "C" fn). The runtime calls the function by name with JSON-encoded arguments. This is simpler to develop, test, and audit — each function is independently callable and discoverable.

Opcode dispatch (DEX and prediction contracts): A single call() export reads a leading opcode byte from get_args() and dispatches internally via match opcode { ... }. This pattern was used for the 7 DEX contracts and the Prediction Market to support batched operations and shared initialization. New contracts should use named exports.

Rationale: Named exports provide better tooling support (function discovery via WASM introspection), clearer error messages (unknown function vs. unknown opcode), and simpler SDK integration. The opcode pattern remains a supported runtime contract shape for these deployed modules.

Runtime resolution: Callers do not need to know which pattern a contract uses. The WASM runtime first tries to resolve the function by name as a WASM export. If that fails, it looks up the function in the contract's ABI — if the ABI entry has an opcode field, the runtime calls the call() export with the opcode byte prepended to the arguments. This resolution is fully transparent to RPC callers and SDK users.

Return Code Conventions

The runtime records the WASM return value in transaction history as return_code. callContract and simulation responses expose the same value as returnCode. ABI metadata can declare result_semantics per function so validators decide deterministically whether a non-trapping call commits or reverts. For example, {"kind":"return_code","success_codes":[0]} means any returned code other than 0 is an ABI failure and the transaction's contract state changes are reverted. {"kind":"return_value"} means the return value is data, not a status code. {"kind":"nonzero_return_value"} means the return value is data and 0 is an ABI failure that reverts state changes. Use it for id- or amount-returning write functions where successful results are always nonzero. Value-returning functions with sentinel errors must declare them with failure_codes, for example {"kind":"return_value","failure_codes":[-1,200]}. Production ABIs should declare result_semantics for every callable function that can be reached directly or by cross-contract call.

LICN

Native Coin (like ETH on Ethereum)
NativeNo WASM

LICN is the native coin of the Lichen blockchain — analogous to ETH on Ethereum or SOL on Solana. It is not a smart contract. LICN lives in each account's native spores balance and is transferred via the system program's native transfer instruction. 1 LICN = 1,000,000,000 spores.

Properties
Property Value
SYMBOL "LICN"
DECIMALS 9
INITIAL_SUPPLY 500,000,000 LICN (genesis)
Address [0x00; 32] (zero address = native)
How It Works

Smart contracts that need to handle LICN use the zero address [0u8; 32] as the token address sentinel. The VM provides native account operations (transfer, balance_of) so contracts can move LICN without an intermediate token contract. This is the same pattern as ETH on Ethereum, where the native coin has no ERC-20 contract.

Source overviewRelease-WASM gated

LichenOracle

Price Feeds, Validator Entropy & Attestations
Source overviewActivation separate
